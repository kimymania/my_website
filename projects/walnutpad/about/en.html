Walnutpad

A shared notes application

Overview

Walnutpad is a collaborative note-sharing application that allows users to create rooms where members can write, edit, and organize shared notes.

The project was inspired by a common problem I observed in many small communities I belong to. Groups such as families, couples, clubs, and hobby communities often rely on messaging applications like KakaoTalk for communication. While chat applications are convenient for conversations, important information is easily buried as new messages accumulate, making announcements difficult to find and long-term information difficult to manage.

Walnutpad addresses this by providing a persistent shared workspace instead of a chronological chat feed. Each member can maintain their own notes, while administrators can pin important announcements so they remain easily accessible to everyone. The application is suitable for a wide range of use cases, from families maintaining shared grocery lists to clubs organizing events and equipment checklists.

Key Features

  • Room-based collaboration
  • JWT authentication with access & refresh tokens
  • Role-based permissions (Admin / Member)
  • Rich note editing and organization
  • Pinned announcements

Technical Decisions & System Design

This backend was built around a simple goal: support real-time, room-based collaboration while keeping the system easy to deploy and reason about in production. Most decisions were made to balance simplicity, performance, and operational clarity rather than overengineering.

FastAPI

I chose FastAPI because the project involves a lot of I/O-heavy operations such as database access and room updates. Its async support fits naturally with this workload and keeps the backend lightweight compared to heavier frameworks.

API Design

The API is designed as a RESTful service with versioning at the root level (v1, v2), mainly to allow future changes without breaking existing clients. I tried to keep endpoints resource-based and consistent in structure rather than introducing action-heavy routes.

Database

I used PostgreSQL because the data model is relational by nature (users, rooms, permissions). I needed strong consistency and didn’t want to deal with eventual consistency issues for something like access control.

Schema Management

For database schema management, I use SQLAlchemy with Alembic migrations. Each migration is versioned by timestamp, which makes schema changes traceable and ensures consistent deployment across environments without manual database modifications.

Authentication & Authorization

Authentication uses minimal-claim JWT access and refresh tokens containing only the user ID and expiry. Authorization decisions are resolved server-side through database lookups, which keeps the token purely as an authentication credential rather than embedding permissions.

Cloudflare

I mainly used Cloudflare for DNS and TLS handling. It also reduces direct exposure of the origin server, which simplifies security concerns at the infrastructure level without adding extra backend complexity.

Nginx

Nginx is used as a reverse proxy in front of FastAPI. Since everything runs on a single VM, it’s mostly there to handle routing cleanly and keep the deployment setup straightforward.

Docker

I containerized both the backend and PostgreSQL so the environment is reproducible. This made deployment on the VM predictable and reduced “works on my machine” issues.

CI/CD (GitHub Actions)

I set up a simple GitHub Actions pipeline to run tests and build the Docker image before deployment. This removes manual deployment steps and ensures basic validation happens before changes are deployed.

Testing

For integration tests, I used Testcontainers to spin up a real Postgres instance. This helped avoid discrepancies between local mocks and actual database behavior.

I focused on adding intuitive tests with pytest and coverage to maintain test converages at at least 85%.

Monitoring (Sentry)

I use Sentry to track backend and client errors in production. Important alerts are forwarded to Discord and email so I don’t have to constantly check dashboards.

Backups

Database backups are generated on a schedule and stored in Google Cloud Storage. This was mainly to avoid relying on a single VM for data durability.

Future Implementation

Caching

Caching is not implemented at the current scale, but it was considered for frequently accessed notes or active room metadata. I decided to keep the system simple for now and rely on direct database queries. Introducing caching at this stage would add additional complexity around invalidation, memory usage, and infrastructure management. The system is structured so caching can be added later without changing the API layer.
